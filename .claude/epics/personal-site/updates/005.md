### tests/ (Playwright — anything needing a real browser)

- `tests/helpers/routes.ts` — the 7 known routes + a guaranteed-missing path
  used to exercise the real 404 page through the live preview server.
- `tests/accessibility.spec.ts` — criteria 45-47: axe
  (`wcag2a`/`wcag2aa`/`wcag21aa` tags, which include `color-contrast` so 46
  rides along with 45) on every route × both themes (via `colorScheme`
  emulation, not the toggle — decouples this suite from task 004's
  localStorage implementation), zero serious/critical violations; skip link
  is the first tab stop and actually navigates; a focus-indicator sample
  check on the first 5 tab stops.
- `tests/theme.spec.ts` — criteria 36-39 (dynamic): system dark/light
  defaults, toggle overriding both directions and surviving reload (found
  via `getByRole('button', {name: /theme|dark|light|appearance/i})` — not a
  guessed selector), aria-pressed/aria-checked presence, and a
  DOMContentLoaded-timing check for criterion 39 that forces a theme via the
  **real toggle** (not a guessed localStorage key) then reloads. Uses
  relative luminance rather than epic.md §7.5's exact hex values, since
  those are allowed to be nudged for contrast (§7.5: "if a value fails,
  darken/lighten it").
- `tests/print.spec.ts` — criteria 31 (Download CV button really calls
  `window.print()` — stubbed rather than let through, since headless
  Chromium has no print dialog to resolve), 32 (dark-theme print still
  renders light-bg/dark-text, via luminance), 33 (portrait hidden in
  print), 34 (nav/footer/toggle/download hidden in print), 35 (best-effort:
  `break-inside: avoid` on elements matching `li`/`article`/anything with
  "entry"/"experience"/"education" in its testid or class — skips itself if
  nothing matches yet, since the exact CV entry markup is task 001/002's
  call).
- `tests/motion.spec.ts` — criteria 41-44. **41 is the one built hardest**:
  a real browser context with `javaScriptEnabled: false`, on every route,
  asserting every heading/paragraph/link/list-item under `<main>` has
  `opacity` ≈1, `display` not none, `visibility` not hidden — this directly
  catches a CSS-authored hidden *from* state (e.g. a class baked into the
  markup) that a code-read would miss, because it can only pass if the
  visible state is the actual default with no JS involved at all. 42 uses
  `reducedMotion: 'reduce'` and checks the same element set is already
  settled (opacity ~1, identity transform) **without ever scrolling**. 43
  checks for zero infinite-iteration CSS animations sitewide plus a
  two-snapshot diff of a below-the-fold element at rest. 44 scrolls a
  heading into view, lets it settle, scrolls back to the top, and confirms
  it's still fully visible.
- `tests/layout.spec.ts` — criterion 16 (the mailto CTA has a
  background-fill and is not smaller than the View-CV/LinkedIn/GitHub text
  links, which must have **no** fill) and criterion 51 (no horizontal
  scroll at 320/390×844/768/1280/1920×1080, across all 8 routes).
- `tests/performance.spec.ts` — criterion 49's dynamic half: sums
  `response.body()` bytes for every request the home page makes, asserts
  under ~500KB, and reports the 10 largest resources on failure.

## `scripts.check` line written

```json
"check": "astro check && astro build && oxlint --ignore-path .gitignore && stylelint \"**/*.css\" --ignore-path .gitignore --allow-empty-input && vitest run && playwright test"
```

Chains typecheck → build → lint (JS/TS then CSS) → tests (vitest then
Playwright), per epic.md §9's "one command" requirement. I only touched this
one script entry, as scoped — `dev`/`build`/`preview`/`astro` are untouched,
and I didn't add separate `typecheck`/`lint`/`test` scripts (the check line
inlines every tool invocation directly instead, so it doesn't depend on any
other task adding/renaming scripts).

## Notes for other tasks (not requirements, just what the tests assume)

- I did **not** invent a `data-testid` contract and force it on 001/002 —
  everything queries by semantics instead (roles, accessible names, hrefs,
  visible text), so it should just work against any reasonable
  implementation. The few places I fell back to something more specific,
  I made it lenient (e.g. criterion 35's entry-break-inside check matches
  `li`, `article`, or anything with "entry"/"experience"/"education" in a
  `class`/`data-testid`).
- `tests/theme.spec.ts`/`tests/print.spec.ts` find the theme toggle via
  `getByRole('button', { name: /theme|dark|light|appearance/i })` — as long
  as its accessible name contains one of those words, it'll be found.
- `spec/no-flash.test.ts` expects the inline theme script's source text to
  literally mention `data-theme` and `localStorage` (e.g.
  `document.documentElement.dataset.theme = ...` or
  `.setAttribute('data-theme', ...)`, plus a `localStorage.getItem(...)`
  call) — this is describing epic.md §7.6 item 6's own spec, not adding a
  new requirement.

## Scope decisions made (epic.md §16 area, my call to make for this task)

  part of `vitest run` inside `pnpm check` — not split into a separate
  opt-in script — because epic.md §12 lists it as a numbered acceptance
