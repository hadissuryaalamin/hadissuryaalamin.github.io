## Coordinator's fixes on top of the agent's work

Two bugs were found while re-verifying `pnpm check` after the agent's
session died — both were **test bugs, not production defects**; no
component/page/style file was changed:

1. **`.stylelintrc.json`** (owned by task 005, not this task, but blocking
   the shared gate): added `"import-notation": "string"` — the default
   `stylelint-config-standard` rule wanted
   `@import url("tailwindcss")`, which conflicts with Tailwind v4's own
   documented `@import "tailwindcss";` convention used in `global.css`.
2. **`tests/accessibility.spec.ts`**: axe was scanning immediately after
   `page.goto()`, sometimes catching the hero's secondary/tertiary link row
   (`.link-quiet`, colour `var(--text)`, ~16-18:1 contrast at rest) mid-fade
   through GSAP's entrance animation, at which point the transient
   opacity-blended colour measured under 4.5:1. Fixed by also emulating
   `reducedMotion: 'reduce'` for the axe pass — `motion.ts` already gates
   all animation registration behind
   `(prefers-reduced-motion: no-preference)` via `gsap.matchMedia()`, so
   under `reduce` nothing ever leaves its authored (fully visible, full
   contrast) state. This is standard practice for a11y CI and also
   exercises the reduced-motion requirement (criterion 42) as a side
   effect. Root cause was test timing, not a real content/contrast defect
   — at rest, `.link-quiet` was always well within AA.
3. **`tests/print.spec.ts`**: criterion-33 (portrait hidden in print) was
   silently *skipping* rather than passing, because it queried
   `page.getByRole('img', { name: /Hadis/i })` *after* switching into print
   media — a correctly `display:none`'d image is excluded from the
   accessibility tree by default, so the query returned zero matches
   whether the portrait was missing *or* correctly hidden, and the test's
   own skip-guard couldn't tell those two cases apart. Switched to a plain
   CSS attribute locator (`img[alt*="Hadis" i]`), which matches
   regardless of visibility, then asserts `.toBeHidden()`. Confirmed the
   feature was already correct — this was purely a test-locator bug.

## Post-epic follow-up: hero right-hand whitespace (2026-08-18)

**Reported:** the hero stacked everything vertically on the left and left the
whole right side empty.

**Confirmed by measurement**, not just by eye. On a 1440px viewport the section
is a 1152px `max-w-6xl` container (1056px content box), and every child was a
full-width block — but `.text-hero-lead` is capped at a `46ch` measure, which
renders 696px. So the lead's text stopped ~360px short of the container's right
edge, and the 192px portrait sat in its own full-width row *underneath* the
text rather than beside it. Nothing filled the right half.

**Fix:** `src/components/Hero.astro` only — the section becomes a two-column
grid at `xl` (`xl:grid xl:grid-cols-[minmax(0,1fr)_auto]`), text in column 1,
portrait alone in column 2, `xl:self-center` against the full text block.

Constraints that shaped it (full rationale in the component's header comment):

- **DOM order is unchanged.** §5.1a fixes the order (h1, lead, meta, portrait,
  CTAs) and `motion.ts`'s `animateHero` collects `[data-animate-item]` by
  document order, so the stagger depends on it. Wrapping the text in a column
  div would have pushed the portrait after the CTA row; instead each child is
  placed explicitly by grid line, which leaves order and the mobile stack
  untouched.
- **The meta line is the binding constraint.** It needs 790px for one line. A
  192px portrait + 48px gap leaves column 1 at 816px (26px slack, constant at
  every width ≥1280 since the container caps at 1152). Enlarging the portrait
  to 224/256px, or widening the gap, both split the degree name as
  "…Machine Learning and Computer | Vision, ANU" — so neither was kept.
- **`xl`, not `lg`.** In the 1024-1279px band the content box is only ~960px,
  so a side-by-side portrait forces that same meta wrap — a regression, since
  that band is one line today. Those widths stay stacked. `xl` still covers
  1366/1440/1536/1920.

**Result at 1440px:** portrait moves to x 1057-1247, vertically centred; hero
height drops 759px → 547px (the portrait's own row is gone, so About rises).
Below 1280px nothing changes at all.

**Verified:** `pnpm check` fully green again (`astro check` 0 errors/0 warnings,
build, oxlint, stylelint, vitest 245/245, playwright 81/81 — including
criterion 51 no-horizontal-scroll at 1920x1080 and criterion 41 no-JS). Layout
probed at 390/768/1023/1024/1279/1280/1366/1440/1536/1920/2560px: stacked below
1280, two-column at and above it, meta on one line at every `xl` width, no
horizontal overflow anywhere.

## Post-epic follow-up round 2: hero orientation, prose measure, metric alignment (2026-08-18)

Three items of client feedback on the round-1 hero work.

### 1. Portrait to the left, name and brief to the right

The round-1 grid put the portrait in column 2. Flipped to
`xl:grid-cols-[auto_minmax(0,1fr)]` with the portrait at `col-start-1` and the
text at `col-start-2`. DOM order is still the §5.1a order — the portrait is
fourth in source and only *renders* first, so `animateHero`'s document-order
stagger is untouched. The column budget is unchanged (`auto` + `1fr`), so the
meta line still has 816px against the 790px it needs: verified still one line
at 1280/1366/1440/1536/2560px.

Known consequence, accepted: the hero's text column now starts at x=432 while
every other section's heading starts at x=192, so the hero reads as indented
relative to the rest of the page. That is inherent to putting the portrait in
the left column inside a shared container.

### 2. Prose measure widened 68ch to 90ch

Reported as the About section's margin not aligning with the other sections and
leaving the right side empty. Measured first: all five sections do share an
identical container (192..1248 at 1440px). The inset was entirely
`.prose-measure`, which capped About, Other work, Contact and the CV/detail
pages at ~713px inside a 1056px content box while the uncapped Projects grid
filled it.

Client was offered three fixes — a left rail for the section labels, widening
the measure, or two text columns — and chose widening, with the readability
trade-off stated explicitly. 90ch renders ~965px, so the gap closes from ~330px
to ~91px. Above the 45-75ch comfort range by design; recorded in the CSS comment
so it doesn't read as an accident.

Side effect worth knowing: the featured full-width card's summary shares this
class and *was* bound by the old cap (~992px inner width), so it now sets two
lines instead of three. Half-width cards are ~452px and were never bound.

### 3. Metric strips made to align

Reported as: some numbers on one line, some on three, nothing lining up.
Measured cause — each cell was an independent `flex-col-reverse`, so it
bottom-packed on its own and a two-line label pushed its own value upward. In
one card the value bottoms were 2076 vs 2097 and the label tops 2080 vs 2101;
nothing shared a baseline. Separately, `.text-metric` sizes off the *viewport*
(3vw), so a half-width card got the same 36px as a full-width container while
its cells are only ~134px — about six monospace characters — which is why
"25.62 → 25.18" needed three lines.

Three changes, all in MetricStrip/ProjectCard/global.css:

- From `sm`, cells become row subgrids spanning the list's two tracks: every
  value shares track 1 (`self-end`, so they settle on one baseline), every label
  shares track 2. Only applied when all cells fit one band (at most 3 metrics),
  because with 4 a single `row-gap` would have to serve both the value-to-label
  step and the band-to-band step.
- New `.text-metric-compact` (one step down) for card strips, so the longest
  delta holds in two lines. Detail pages keep the full `.text-metric`.
- The arrow is bound to the value before it with a non-breaking space, so a
  delta can only break after the arrow ("25.62 →" / "25.18") instead of
  stranding the arrow alone on a middle line.
- The card is a flex column with the strip on `mt-auto`, pinning the strip and
  stack line to the card bottom so neighbours in a row line up rather than
  starting at two different heights.

Result: within every card, all three value bottoms and all three label tops now
share a single y, and no value exceeds two lines. GPT-2 and Deep Learning also
now share a stack line at y=2122.

Residual, not fixed: *across* cards the value baselines still differ by up to
~20px, because a card whose labels wrap to three lines pushes its own values up
relative to a neighbour whose labels wrap to two. Closing that needs the label
band, value band and stack line all forced to a uniform height (or a subgrid
chain from the list down through each card), which trades real dead space for
the last 20px. Left alone deliberately.

### Astro gotcha found while doing this

A bare `<` inside a **frontmatter comment** makes the compiler's TSX transform
lose the `Props` interface. `Astro.props` silently degrades to a string-keyed
any-record, and the only symptom is an implicit-any error on a `.map` callback
far below, pointing nowhere near the cause. Cost a few build cycles to isolate;
noted in MetricStrip's own comments. Write element names as prose and spell
comparisons out inside frontmatter comments.
