  - **`<ThemeInit />`** (default, `toggle` omitted/false) — use once, inside
    `<head>`, as early as possible. Renders `<meta name="color-scheme"
    content="dark light">` **and** a hand-written, non-module `<script
    is:inline>` that reads `localStorage.getItem("theme")` and, if it is
    `"light"` or `"dark"`, sets `document.documentElement.setAttribute
    ("data-theme", stored)` — before any paint (criterion 39, no flash).
    This script is *intentionally* not an import of theme.ts: a
    `type="module"` script is deferred by the browser and would run too
    late to prevent the flash, so the minimal read-and-apply logic is
    duplicated by hand. Keep the two in sync if the storage key/attribute
    ever changes.
  - **`<ThemeInit toggle />`** — use once, inside `<nav>`. Renders
    `<button type="button" id="theme-toggle" class="theme-toggle"
    aria-pressed="false" aria-label="Switch between light and dark
    theme">` plus a bundled `type="module"` script that calls
    `initThemeToggle()` from theme.ts to wire up the click handler and keep
    `aria-pressed` in sync. Style via `#theme-toggle` / `.theme-toggle`.

**Attribute/storage contract (binding — must match 002's CSS token file and
any other consumer):**
- localStorage key: `"theme"`
- values: `"light"` | `"dark"` only
- `<html data-theme="light"|"dark">`
- **Attribute ABSENT = no explicit visitor choice → the CSS
  `@media (prefers-color-scheme: dark)` block decides.** Never write any
  other value, never default it to `"light"` on the initial static HTML —
  the epic's §7.6 steps 1–3 (bare `:root` = light values, dark media query
  keyed off `:not([data-theme="light"])`, then `[data-theme="dark"]`
  override) only work if the attribute is truly absent by default.

Verified end-to-end with a temporary smoke-test page (added, built, deleted
— never committed): head script renders as raw inline (not bundled/deferred),
meta tag present, toggle button renders in `<nav>` with correct
`aria-pressed`/`aria-label`, module script correctly wires the click
handler. This satisfies criteria 38–40 mechanically; criteria 36/37 depend
on 002's CSS token file, which this component's absent-by-default behaviour

### Local environment issue found and fixed (read this if `pnpm build` ever reports `MissingSharp`)

This worktree's `node_modules` had an **incomplete pnpm store link for the
optional `sharp` dependency**: `astro`'s own `node_modules/sharp` symlink
was fine, but sharp's *own* nested dependency links
(`node_modules/.pnpm/sharp@0.35.3/node_modules/sharp/node_modules/`) were
missing `detect-libc`, `semver`, and `@img/colour` entirely (only `.bin/`
was present) — likely an artifact of how this worktree's `node_modules` was
populated rather than a fresh `pnpm install`. This made every build-time
image transform throw `MissingSharp`.

Fixed by restoring the missing links as plain filesystem operations — **no
`pnpm add`/`pnpm install` was run, package.json and pnpm-lock.yaml are
untouched**:
- `node_modules\sharp` → NTFS junction to
  `node_modules\.pnpm\sharp@0.35.3\node_modules\sharp` (a Git-Bash `ln -s`
  attempt silently produced a stale one-time *copy* instead of a live link
  on this Windows setup — a real junction via PowerShell's
  `New-Item -ItemType Junction` was needed instead).
- Three matching junctions inside
  `node_modules\.pnpm\sharp@0.35.3\node_modules\sharp\node_modules\` for
  `detect-libc`, `semver`, and `@img\colour`, pointing at their existing
  entries elsewhere in the pnpm store.

All of this lives inside the gitignored `node_modules/`, so **it is not
committed and will not survive a fresh `pnpm install`** in this worktree or
in CI. It only proves the `astro:assets`/`<Picture>` pipeline is correct
and hits budget once sharp is linked correctly. If a clean install (locally
or in CI) hits `MissingSharp` again, the durable fix is either a normal
`pnpm install` (which should link it correctly on a fresh store) or adding
`sharp` as an explicit direct `dependency` in `package.json` so pnpm always
places a root-level link — I did not do this myself since it requires
`pnpm add`, which I was told not to run; noting the exact package name here
per the dependency rule.
